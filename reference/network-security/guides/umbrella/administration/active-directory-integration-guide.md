# Active Directory Integration Guide — Cisco Umbrella

## Overview

Cisco Umbrella's AD integration enables user and group-level policies and reporting. Without AD integration, Umbrella can only identify traffic by roaming client (device) or network IP — it cannot attribute DNS queries to specific users or apply per-user or per-group policies.

AD integration uses the **Umbrella Virtual Appliance (VA)** — a lightweight proxy deployed in your environment that reads AD event logs and maps user logon events to IP addresses, then sends this mapping to Umbrella.

---

## Architecture

```
Domain Controller
    ↓ (Event log: security event 4768/4769 — Kerberos logon)
Umbrella Virtual Appliance (VA)
    ↓ (User-to-IP mapping, encrypted)
Umbrella Cloud
    ↓
DNS query from 10.1.1.50 → mapped to → jane.smith@corp.com
    ↓
Policy for jane.smith or her AD group applies
```

**What the VA does:**
- Reads Windows Security Event Log from domain controllers (events 4768, 4769 — Kerberos ticket events that indicate user logons)
- Maps the authenticated username to the source IP at the time of logon
- Forwards this mapping to Umbrella over HTTPS (port 443 outbound)
- The mapping remains valid until the user logs off or the lease expires (default 4 hours)

**What the VA does not do:**
- The VA does not proxy DNS traffic
- The VA does not store credentials or passwords
- The VA does not require inbound firewall rules

## Pre-Deployment Requirements

| Requirement | Details |
|---|---|
| Hypervisor | VMware ESXi, Hyper-V, or KVM |
| VM resources | 4 vCPU, 4 GB RAM, 80 GB disk |
| Network | Static IP on internal network, access to DCs on port 9389 (AD Web Services) and port 636 (LDAPS) |
| Outbound connectivity | HTTPS (port 443) to `registration.uda.cisco.com` and `*.umbrella.com` |
| Active Directory | Windows Server 2012 R2 or later domain controllers |
| Domain controller audit policy | Enable "Audit Kerberos Authentication Service" and "Audit Kerberos Service Ticket Operations" in the Default Domain Policy |

## Step 1 — Enable Audit Policy on Domain Controllers

The VA reads Windows Security Event Log. The relevant events (4768, 4769) are generated by Kerberos authentication — these must be enabled in the domain audit policy.

**Via Group Policy (apply to all DCs):**
1. Open Group Policy Management on a DC
2. Edit the **Default Domain Controllers Policy** (do not create a new GPO for this — the Default Domain Controllers Policy applies to the Domain Controllers OU)
3. Navigate to: `Computer Configuration → Policies → Windows Settings → Security Settings → Advanced Audit Policy Configuration → Account Logon`
4. Enable:
   - **Audit Kerberos Authentication Service** → Success
   - **Audit Kerberos Service Ticket Operations** → Success
5. Apply: `gpupdate /force` on all DCs

**Verify events are being generated:**
On a DC, open Event Viewer → **Windows Logs → Security** → filter for Event IDs 4768 and 4769. These should appear every time a user authenticates.

---

## Step 2 — Download and Deploy the Virtual Appliance

1. In Umbrella: **Deployments → Core Identities → Active Directory → Download VA**
2. Choose the format for your hypervisor (OVA for VMware, VHD for Hyper-V)
3. Import the VA:

**VMware ESXi:**
1. vSphere Client → **File → Deploy OVF Template**
2. Upload the downloaded OVA
3. Configure network: assign to the internal VLAN where DCs are reachable
4. Power on the VM

**Hyper-V:**
1. Hyper-V Manager → **Import Virtual Machine**
2. Browse to the extracted VHD
3. Configure: Generation 1, 4 GB RAM, connect to internal virtual switch
4. Start the VM

---

## Step 3 — Configure the VA

After powering on the VA, access its console (VMware console or Hyper-V connect):

**Default credentials:** `admin` / `umbrella` — change immediately after first login.

**Initial setup wizard:**
1. Set hostname: `umbrella-va01` (or follow naming convention)
2. Configure network:
   ```
   IP Address: 10.0.1.50       (static IP on your internal network)
   Subnet mask: 255.255.255.0
   Default gateway: 10.0.1.1
   DNS servers: 10.0.1.10      (internal DNS — not Umbrella resolver)
   ```
3. Configure NTP server (use an internal NTP or `time.umbrella.com`)
4. Register with Umbrella:
   - Provide your Umbrella Admin credentials (or use the API token from **Admin → API Keys**)
   - The VA registers itself with your organisation

**Verify registration:**
In Umbrella: **Deployments → Core Identities → Active Directory** — the VA should appear with status **Active**.

---

## Step 4 — Connect the VA to Domain Controllers

The VA needs to read event logs from your DCs.

1. In the VA admin console: **Configuration → Active Directory → Add DC**
2. Enter:
   | Field | Value |
   |---|---|
   | DC hostname/IP | Internal IP or FQDN of the domain controller |
   | Domain | `corp.local` (your AD domain) |
   | AD Web Services port | `9389` (default) |
   | Service account | `CORP\umbrella-svc` (see below) |
   | Password | Service account password |

**Required service account permissions:**
The VA requires a read-only service account with access to the DC's event log.

```powershell
# Create the service account in AD
New-ADUser -Name "Umbrella VA Service" `
    -SamAccountName "umbrella-svc" `
    -UserPrincipalName "umbrella-svc@corp.local" `
    -AccountPassword (Read-Host -AsSecureString) `
    -Enabled $true `
    -PasswordNeverExpires $true

# Add to Event Log Readers group (allows reading Security event log)
Add-ADGroupMember -Identity "Event Log Readers" -Members "umbrella-svc"
```

**Note:** The service account does not need Domain Admin or any elevated permissions. Event Log Readers is sufficient.

---

## Step 5 — Verify AD User Mapping

After connecting the VA to your DCs:

1. Have a test user log in to a workstation on the network
2. In Umbrella: **Deployments → Core Identities → Active Directory → Users** — the user should appear with their current IP mapping
3. In Activity Search: **Reporting → Activity Search** — filter by the user's name — their DNS activity should appear with the username attributed

**Expected time to see mapping:** 2–5 minutes after the user authenticates.

---

## Step 6 — Create AD-Based Policies

With users visible in Umbrella, you can now create policies that target AD users or groups:

1. **Policies → Management → DNS Policies → Add DNS Policy**
2. In the **Policy Identities** tab, select **AD Users** or **AD Groups**
3. Search for and select the users or groups
4. Configure security/content settings appropriate for that group
5. Save and review policy ordering (see [Policy Management and Precedence Guide](policy-management-and-precedence-guide.md))

**Common group-based policies:**

| Group | Policy notes |
|---|---|
| IT Admins | Allow technical domains (developer tools, security research tools) that may be blocked for general staff |
| Executive team | Add to VAP-equivalent policy with strict security but relaxed content filters |
| Finance | Allow specific finance SaaS domains; block personal file sharing |
| Students / Guest | Restrictive content filtering |

## Why Users Go Missing From Reports

This is one of the most common AD integration support calls. Users appear in reports for a while then stop being attributed by name.

### Cause 1 — User IP Changes Without Re-Authentication

The VA maps users to IPs based on Kerberos logon events. If a user's IP changes (DHCP lease renewal, switching between wired and Wi-Fi) without triggering a new Kerberos event, the mapping goes stale.

**Fix:** Reduce DHCP lease time (increases re-authentication frequency) or configure DHCP lease renewal events to trigger a VA update. Alternatively, use domain-joined machines where users are logged in — Kerberos ticket renewals (event 4769) keep the mapping fresh.

### Cause 2 — VA Cannot Reach Domain Controller

If the VA loses connectivity to a DC (firewall rule change, DC restart, network change):

**Diagnose:**
- VA admin console → **Status → DC Connections** — check DC connectivity status
- Test from VA: `Test-NetConnection -ComputerName dc01.corp.local -Port 9389`

**Fix:** Restore network connectivity or add the firewall rule allowing VA → DC on port 9389.

### Cause 3 — Service Account Password Expired

If `PasswordNeverExpires` was not set on the VA service account, the password will expire per domain policy.

**Fix:** Reset the service account password and update in the VA configuration. Set `PasswordNeverExpires` going forward (or use a managed service account — gMSA).

### Cause 4 — VA is Unhealthy / Needs Restart

**Diagnose:** In Umbrella → **Deployments → Core Identities → Active Directory** — check VA status. If it shows "Inactive" or "Error":

**Fix:**
```bash
# SSH to VA and check service status
sudo systemctl status umbrella-agent
sudo systemctl restart umbrella-agent
```

### Cause 5 — Kerberos Audit Events Not Generating

If events 4768/4769 stopped appearing on DCs (audit policy was changed):

**Diagnose:** Event Viewer on DC → Security log → filter for 4768/4769. If none appear after multiple user logons, audit policy is disabled.

**Fix:** Re-apply the audit policy from Step 1 and run `gpupdate /force` on all DCs.

## High Availability — Multiple VAs

For environments with multiple sites or redundancy requirements:

- Deploy one VA per site (on the same LAN segment as the site's DCs for low latency)
- Each VA registers independently with the Umbrella organisation
- Umbrella aggregates the user-IP mappings from all VAs
- If one VA goes offline, the other VAs continue to provide mapping for their site

**VA placement:** Deploy the VA close to the DCs it reads from. Latency between VA and DC affects how quickly user mappings update. On a large campus, co-locate the VA with the primary DC.
