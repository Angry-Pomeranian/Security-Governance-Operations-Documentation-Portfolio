# Windows Hello for Business — Deployment Guide

## Overview

Windows Hello for Business (WHfB) replaces passwords with hardware-backed credentials tied to a device's TPM (Trusted Platform Module). The user's private key is generated by and never leaves the TPM — authentication is a local gesture (PIN, fingerprint, or face) that proves possession of the device-bound key.

WHfB is phishing-resistant by design: there is no password to steal, and credentials are scoped to a specific Entra ID tenant (the relying party), so they cannot be replayed on attacker-controlled sites.

This guide covers deployment. For Intune policy configuration settings, see [`../../policies/conditional-access/windows-hello/README.md`](../../policies/conditional-access/windows-hello/README.md).

---

## Deployment Paths

| Trust Model | Requirements | Complexity | Recommended For |
|---|---|---|---|
| **Cloud Trust** | Entra ID + Intune; no on-prem PKI | Low | Entra-only tenants; most hybrid tenants |
| **Key Trust** | Hybrid AAD join + on-prem AD DS + no PKI | Medium | Hybrid environments without PKI |
| **Certificate Trust** | Hybrid AAD join + on-prem PKI + ADFS or connector | High | Legacy environments with existing PKI investment |

**Recommendation:** Cloud Trust for all new deployments. It eliminates the need for on-prem PKI and ADFS while providing full feature parity including on-prem resource access.

## Prerequisites

### Device requirements
- Windows 10 21H2 or later / Windows 11 (all versions)
- TPM 2.0 enabled in BIOS/UEFI (TPM 1.2 is blocked by policy recommendation)
- Secure Boot enabled
- Entra ID joined **or** Hybrid Azure AD joined
- Device enrolled in Microsoft Intune

### Identity and licensing
- Entra ID P1 or P2 license (included in M365 E3/E5, Business Premium)
- Users must have completed MFA registration (used to verify identity during WHfB setup)

---

## Step 1: Enable WHfB in Entra ID (optional — managed via Intune instead)

For Intune-managed deployments, configure WHfB entirely through Intune configuration profiles (Step 2). If you want to set a tenant-level default, navigate to:

`Entra ID → Devices → Windows Hello for Business`

Set to **Enabled** or leave as **Not configured** (let Intune manage it per-device group).

---

## Step 2: Deploy via Intune — Cloud Trust Configuration

1. **Create a configuration profile:**
   - Intune portal → Devices → Configuration profiles → Create → Windows 10 and later
   - Profile type: **Settings Catalog**
   - Search: `Windows Hello for Business`

2. **Key settings to configure:**

| Setting | Value | Purpose |
|---|---|---|
| Use Windows Hello for Business | Enabled | Turns WHfB on for enrolled devices |
| Use Cloud Trust for On-Prem Auth | Enabled | Eliminates need for ADFS/PKI for on-prem resource access |
| Use a hardware security device | Required | Enforces TPM 2.0; blocks software-based key storage |
| Minimum PIN Length | 6 | Sets minimum PIN complexity |
| Require Security Device | True | Blocks enrollment on devices without TPM |

3. **Assign** the profile to your target device group (e.g. `grp-whfb-pilot`)

See [`../../policies/conditional-access/windows-hello/README.md`](../../policies/conditional-access/windows-hello/README.md) for the full settings table including Credential Guard, Enhanced Sign-in Security, anti-spoofing, FIDO2, and PIN history.

---

## Step 3: Enforce via Conditional Access (recommended)

Create a Conditional Access policy requiring **Authentication strength: Phishing-resistant MFA** for high-value apps (e.g. all cloud apps, admin portals). WHfB satisfies phishing-resistant MFA; passwords do not.

This gradually pushes users toward WHfB or FIDO2 keys without hard-blocking access during the rollout period.

---

## User Enrollment Flow

Once the Intune policy is applied, enrollment is triggered on the user's next sign-in:

1. User signs in to Windows with their Entra ID credentials + MFA
2. Windows detects WHfB is required and prompts: **"Your organisation requires Windows Hello"**
3. User verifies identity (satisfies MFA via Authenticator push or TAP)
4. TPM generates a key pair; public key is registered with Entra ID
5. User sets a PIN (and optionally enrols biometric — fingerprint or face)
6. Future sign-ins use only the local gesture; no password required

## Verification

**On the device:**
```powershell
# Check join status and Hello provisioning
dsregcmd /status
```
Look for:
- `AzureAdJoined : YES`
- `NgcSet : YES` (WHfB provisioned)
- `NgcKeyId : <key GUID>` (TPM-bound key ID)

**Event Viewer:**
- Path: `Applications and Services Logs → Microsoft → Windows → HelloForBusiness → Operational`
- Event ID **300**: WHfB provisioning succeeded
- Event ID **301**: WHfB sign-in succeeded

**Intune portal:**
- Devices → select device → Configuration profiles → `Windows Hello for Business` profile → Status: **Succeeded**

## Troubleshooting

| Issue | Likely Cause | Fix |
|---|---|---|
| `NgcSet: NO` after policy applies | TPM not enabled or TPM 1.2 in use | Enable TPM 2.0 in BIOS; check firmware |
| Enrollment prompt never appears | Device not AAD joined or policy not applied | Run `dsregcmd /status`; check Intune sync |
| "Your PIN can't be set" error | Azure AD Kerberos not configured (Cloud Trust) | Enable Azure AD Kerberos: `Set-AzureADKerberosServer` |
| Biometric option missing | No ESS-certified sensor | Only certified sensors supported; check driver |
| Credential Guard conflicts | VBS not enabled | Confirm Secure Boot + UEFI firmware; check `msinfo32` |
