## Implement and Manage User Identities (20–25%)

* 🟢 **Microsoft Entra ID (Azure AD)** – Cloud-based identity and directory service to manage users, groups, devices, and applications. Treat identity as your new security perimeter (Zero Trust mindset). A single Entra tenant often serves as the **authoritative identity source** for an organization, including hybrid scenarios. Entra ID combines core directory services, application access management, and identity protection in one solution.

* 🟢 **Entra Roles & Administrative Units:** Entra ID provides **built-in roles** (like Global Administrator, User Administrator, etc.) applying the principle of least privilege for admin tasks. You can also create **custom roles** with fine-grained permissions. By default, role assignments apply to the entire tenant. Use **Administrative Units (AUs)** to delegate role scope to specific departments or regions – e.g. allow a Helpdesk Admin to manage only users in the "Marketing" AU. AUs act as containers for users, groups, or devices; roles scoped to an AU can manage only those members. *(Example:* University IT can create separate AUs per school, each with its own user admins.*)* AUs cannot be nested and currently aren’t used in Entra ID Governance.

* 🟢 **Tenant Configuration:** Verify and **manage custom domains** for your tenant (e.g. `contoso.com` in addition to the default `contoso.onmicrosoft.com`). Configure **Company Branding** (sign-in page logo, background, custom help text) to provide a familiar login experience. Review **user settings** (e.g. who can invite guests, whether users can register applications, etc.), **group settings** (like self-service group management options), and **device settings** (max devices per user, Azure AD join/registration settings) in the Entra admin center to align with organizational policies.

* 🟢 **Users and Groups:** Create and manage user identities individually or in bulk. Users can be added manually, in bulk via CSV/PowerShell, or automatically from HR systems (with Identity Lifecycle management). **Groups** help manage access at scale – use Security groups (for access control) and Microsoft 365 groups (for collaboration, includes Teams/SharePoint features). Enable **dynamic groups** to auto-update membership based on user attributes (requires P1 license). Assign licenses to users or (with P1) use **group-based licensing** to automate license management. Leverage **custom security attributes** if needed to tag objects with organization-specific attributes for advanced scenarios (like building dynamic rules or custom logic).

* 🟢 **Device Identity:** Implement device management by **registering or joining devices** to Entra ID. *Azure AD registered* devices (bring-your-own devices using personal MS account or Entra ID registration) and *Azure AD joined* devices (corporate-owned, Windows 10/11 devices joined directly to Entra ID) enable device-based Conditional Access. *Hybrid Azure AD joined* devices are joined to on-prem AD and registered with Entra ID (for hybrid environments). Configure device **conditional access** policies and compliance integration (with Intune) to ensure only trusted devices access resources.

&#x20;*Illustration of a hybrid identity setup: connecting on-premises AD to Microsoft Entra ID for a unified identity (via synchronization). Users enjoy one identity for both cloud and on-prem resources.*

* 🟢 **Hybrid Identity (Azure AD Connect):** Bridge your on-premises Active Directory with Entra ID using **Microsoft Entra Connect** (or Cloud Sync) to establish a *hybrid identity*. This creates a common user identity for authentication and authorization to all resources, regardless of location. **Synchronization** keeps on-prem AD users, groups, and passwords in sync with Entra ID. **Password Hash Synchronization (PHS)** is recommended even if using federation, as a backup and to enable leaked credential detection. Alternatively, **Pass-Through Authentication (PTA)** allows Entra ID to validate passwords against on-prem AD in real-time (without storing password hashes in the cloud). **Federation (AD FS)** can be used for on-premises authentication, but many organizations are moving away from AD FS to simplify and use cloud auth. Enable **Seamless SSO** so domain-joined devices auto-authenticate to Entra ID services without repeated prompts. Monitor sync health via **Entra Connect Health** for AD DS, ADFS, and sync – it provides alerts and insights into identity synchronization and sign-in errors. *(*🟠 *Tip:* Don’t sync on-premises high-privilege accounts (e.g. Domain Admins) to Entra ID – the default Entra Connect filtering excludes them for security.*)*

* 🟡 **Licensing Note:** Most core Entra ID features (user/group management, basic sync) are available with the free tier, but advanced capabilities (AUs, dynamic groups, Identity Governance features, conditional access, Identity Protection, etc.) require **Entra ID P1/P2** licenses. Ensure admin accounts have the necessary licenses if managing premium features (e.g. an AU-scoped administrator needs at least P1).

* 🔴 **Break-glass Accounts:** Maintain at least two emergency admin accounts that are **not subject to Conditional Access or MFA** (used only when normal admin access fails). These accounts (Global Administrators) should be highly secured (strong passwords, hardware token or vault storage) and monitored (sign-in alerts) – they act as a safety net if, for example, MFA services are down or all admins get locked out. Exclude them from risky policies and don’t use them daily.

## Implement Authentication and Access Management (25–30%)

* 🟢 **Authentication Methods:** Microsoft Entra supports a variety of auth methods beyond just passwords. Strengthen identity security by requiring **Multi-Factor Authentication (MFA)** – something users know + have/are. Common MFA/Passwordless methods include: **Microsoft Authenticator** app notifications, **Authenticator Lite** (approval via Outlook app), **FIDO2 security keys** (passwordless “passkeys”), **Certificate-based authentication**, **SMS codes**, **Voice calls**, **OATH** hardware/software tokens, and **Temporary Access Pass (TAP)** for one-time onboarding. Also leverage **Windows Hello for Business** for passwordless sign-in using biometrics/PIN tied to the device’s TPM (can be configured via key trust, cert trust, or cloud trust depending on hybrid needs). Each method has its use cases – plan which to deploy based on user needs and security (e.g. FIDO2 for high-value accounts, Authenticator for most users, SMS/voice as fallback).

* 🟢 **Planning for Secure Authentication:** Enable **Microsoft Entra multifactor authentication** tenant-wide to reduce password-only attacks. By requiring two or more factors (something you know, have, or are), you mitigate risks from weak or leaked passwords. Consider a **passwordless** strategy: users authenticate with biometrics or keys that tie to cryptographic credentials, removing passwords from the equation. *(*🟠 *Tip:* Roll out passwordless gradually – e.g., start with VIP users or IT admins using FIDO2 keys or Windows Hello, then expand.*)* For any remaining password usage, enforce **Microsoft Entra Password Protection** to ban common passwords. This feature checks new passwords against global and custom banned password lists to prevent easily guessable passwords. It works for both cloud accounts and (with an agent) on-prem AD, helping eliminate weak passwords across the board.

* 🟢 **Tenant-wide MFA Settings:** Choose an MFA deployment: **Security Defaults** (one-click enable of basic MFA for all users using Authenticator app) or custom Conditional Access policies. Legacy per-user MFA management is deprecated in favor of Conditional Access. Many tenants start with security defaults (all users register Authenticator app, with MFA required for critical operations), then move to tailored **Conditional Access** policies for finer control. Example Conditional Access rules: require MFA for all users but exclude trusted locations (office network), or require MFA for admins at every login, or block login from countries where your organization doesn’t operate. **Conditional Access** evaluates signals (user, location, device, app, risk) and enforces controls (e.g., require MFA, require compliant device, block access) to allow/deny access. You can have policies that **allow regular sign-in** when on a compliant device or trusted network but **prompt for MFA** when off-network or on personal devices.

&#x20;*Conditional Access policy flow: various signals (user risk, location, device state, app sensitivity) are evaluated to decide if a user can access an app, needs to perform MFA, or is blocked. This ensures only legitimate, trusted sessions access corporate resources.*

* 🟢 **Self-Service Password Reset (SSPR):** Implement SSPR to empower users to reset their own passwords securely, reducing helpdesk calls. **Integrate SSPR with MFA registration** – Entra ID allows users to register for MFA and SSPR in one combined experience, populating methods for both. Configure SSPR policies (who is allowed to use SSPR, what methods are required – e.g., phone, email, or security questions (for AD on-prem)) and enable password writeback if using hybrid (so resets in the cloud update your on-prem AD passwords). Remind users to keep their verification info up to date via the **My Profile** page.

* 🟢 **Account Lockout & Session Management:** Enforce strong lockout policies (Entra ID has default lockout after 10 failed attempts, auto-unlock in 1 minute for cloud accounts; on-prem AD lockout as per your GPO). When a user is compromised or leaves, **disable their account** (Block sign-in = true) promptly. **Revoke sessions** to sign them out of any active sessions – in Entra ID, an admin can revoke a user’s refresh tokens which forces re-authentication on all devices (e.g., using PowerShell `Revoke-AzureADUserAllRefreshToken` or via the Entra portal’s “Revoke Sessions” button). This ensures a user who is disabled or whose password is reset is signed out everywhere.

* 🟢 **Azure AD Kerberos for Hybrid** (Cloud Kerberos Trust): New integration allows Azure AD-joined devices to access on-prem file shares or printers via a cloud Kerberos ticket granting ticket (TGT) issued by Entra ID. In a hybrid environment, this feature (currently evolving) can simplify authentication by removing the need for AD FS or Azure AD Connect PTA for certain Kerberos scenarios. *(*🟠 This relates to Windows Hello cloud trust deployment – the Azure AD Kerberos service issues tickets for on-prem AD on behalf of the user’s Azure AD credentials.*)* If included in the exam, remember it’s a method to let cloud-authenticated users access on-prem resources seamlessly without traditional Kerberos infrastructure on the client side.

* 🟡 **Monitoring Sign-in Risk:** Although more in-depth Azure AD Identity Protection is outside the core SC-300 objectives, be aware of **Identity Protection** features if you have P2: it automatically detects risky sign-ins (impossible travel, unfamiliar locations, known breached creds) and risky users, and can enforce risk-based policies (e.g., require MFA if sign-in is deemed risky, or disable user if highly compromised). This ties into authentication as another layer of adaptive security, and the **Identity Secure Score** gives points for having MFA on all users, SSPR enabled, etc., guiding you to improve auth security.

* 🔴 **Common Pitfalls:** Avoid allowing unprotected authentication – ensure **MFA is enforced for all admin accounts** and any user with privileged access. Don’t ignore **password policies** just because MFA is on; a weak password can still be a liability if MFA is temporarily not required. Regularly **review accounts** (especially guest and inactive accounts) – disable or remove those no longer needed to reduce attack surface.

## Plan and Implement Workload Identities (20–25%)

* 🟢 **Workload Identities Overview:** Identities aren’t just for humans – applications and services also need identities for authentication (often called *service principals* or *app identities*). In Entra ID, **workload identities** include app registrations, service principals, and **Managed Identities**. **Managed identities** for Azure resources are a key feature to simplify credential management for applications. Instead of apps storing secrets or keys to authenticate to Azure services, an Azure resource (like a VM, Web App, or Function) can be assigned a managed identity and use it to get tokens **without managing any secret** – Azure handles the credentials internally. This eliminates the risk of secret leaks and the burden of rotation.

* 🟢 **Managed Identities (System vs User-Assigned):** There are two types:

  * **System-Assigned Managed Identity:** Enabled directly on an Azure resource (e.g., a VM, App Service). Azure creates a service principal in Entra ID tied to that resource’s lifecycle. When the resource is deleted, its identity (service principal) is automatically removed. **Scope:** one resource – it *cannot be shared* with others. Use case: a single app or VM needs to access Azure resources (storage, database) – enable its system-assigned identity and grant it appropriate RBAC roles on the target resource.
  * **User-Assigned Managed Identity:** An independent Entra ID resource that you create, which results in a service principal not tied to any one compute resource. You can **assign this identity to one or more Azure resources** (for example, multiple VMs or functions can all use the same user-assigned identity). You manage its lifecycle (create/delete explicitly). Use case: a microservices cluster where multiple components need the same access to a storage account – create one user-assigned identity and attach it to all components so they share credentials. *User-assigned MIs are recommended for scenarios where workloads need a stable identity across resources or need pre-creation to assign permissions beforehand.*

  For either type, once the managed identity exists, **authorize it** by granting it roles on Azure resources (e.g., give it Reader on a Key Vault or Contributor on a storage account). Then code running on that resource can request a token for the target resource’s scope and call it – no passwords or keys required. Managed identities work for any Azure service that supports Entra ID auth (and even your own applications).

* 🟢 **Service Principals & App Registrations:** A **Service Principal** is the Entra ID representation of an application in a tenant (it’s like an account for the app). When you register an app (create an **App Registration**), an application object is created (global definition) and a service principal is created in your home tenant (and more service principals can exist in other tenants if the app is multi-tenant or given access via consent). *For the exam:* remember that *Enterprise Applications* in the Entra admin center refer to service principals (instances of apps), whereas *App Registrations* refer to the application objects (with client IDs, permissions, etc).

* 🟢 **Enterprise App Integration:** Plan how to integrate SaaS and line-of-business apps:

  * **Gallery SaaS Apps:** Microsoft provides a gallery of thousands of pre-integrated apps supporting SSO (SAML/OIDC) and automated user provisioning. You can *assign users or groups* to these enterprise applications to control who has access.
  * **Single Sign-On (SSO):** Enable SSO so users can access apps with their Entra ID credentials. SAML 2.0 and OIDC/OAuth2 are common protocols. For SAML apps, you’ll configure Entra ID as IdP with claims mapping, etc. For OIDC/OAuth apps, you might just use app registration or gallery config.
  * **Tenant-wide vs App-specific settings:** **User consent settings** are important – by default, users can consent to low-risk app permissions for multi-tenant apps. Admins can restrict *user consent* to apps, requiring an admin to grant permissions for any new app (to prevent rogue apps). There’s an **Admin consent workflow** feature where users can request admin approval for an app they tried to use. At a tenant level, you can also configure if users can register their own applications (which creates app registrations/service principals).
  * **App Roles and Groups:** Some enterprise apps and custom apps support **App Roles** – defined in the app registration (e.g., Admin, User roles for the app). These roles can be assigned to users or groups, and users receive role claims in their token. Use this to manage app-specific authorization via Entra ID assignments rather than inside the app.
  * **Application Proxy:** Use the Azure AD Application Proxy to publish on-premises web applications to external users securely. The App Proxy connector runs on-prem and communicates outbound to Azure, so external users hit a cloud endpoint. Conditional Access and Entra ID SSO can be applied to these apps, providing **secure remote access without VPN**. Great for legacy web apps: an on-prem app can use Kerberos delegation via App Proxy so Entra ID pre-authenticates the user and then signs into the on-prem app on their behalf.
  * **Workload Identity Delegation:** If an application needs to act on Azure resources, you might use an **Azure AD service principal** with a client secret or certificate. However, managed identities are easier for Azure-hosted apps. For third-party or on-prem apps that can’t use managed identity, you might create an **Entra application (service principal)**, generate a client secret or cert, and use that for auth (this is essentially creating a service account for the app).

* 🟢 **App Registration Process:** When planning app identity:

  1. **Plan** whether the app is single-tenant (only your org) or multi-tenant (others can consent to it), and what redirect URIs and permissions it needs. Decide who in your org is allowed to register apps (you can restrict this to admins).
  2. **Register the App:** Give it a name and configure sign-in audience (accounts in this tenant, multi-tenant, etc.). This creates an **Application (client) ID**.
  3. **Authentication Setup:** Configure **platform settings** (Web, SPA, Mobile) and add **Redirect URIs** where tokens should be sent. If needed, set **Logout URL**, enable **Implicit grant** (for SPA legacy flows) or Authorization Code with PKCE (modern), etc.
  4. **Credentials:** Generate a **Client Secret** or upload a **Certificate** for the app to authenticate with Entra ID (for confidential server-side apps). Always treat these as sensitive (client secrets are like passwords) – store in Key Vault or use managed identity for Azure apps to avoid secrets entirely.
  5. **API Permissions:** Define what APIs this app needs to call. This could be Microsoft Graph, other Microsoft APIs, or your own API. Add **delegated permissions** (on-behalf-of a user) or **application permissions** (app-level). If application permissions or any permission requiring admin consent are added, you (Global Admin) must **grant admin consent** to those permissions for your org.
  6. **App Roles & Scopes:** (If building your own app/API) Define **App Roles** for your app’s own authorization needs, and/or define OAuth2 **scopes** your API can expose for client apps to request. This is done in the app registration manifest or GUI, and can then be assigned to users or applications.
  7. **Enterprise Application (Service Principal):** When the app is used in your tenant, a service principal is created under Enterprise Apps. Configure any **user assignments** (you can require assignment such that only users/groups explicitly given access can sign into the app) and set **self-service** options if applicable (users requesting access).
  8. **Consent and Usage:** Users (or admins) consent to allow the app to access the specified resources. Monitor the enterprise app’s sign-in logs and audit logs for usage or issues.

* 🟢 **Monitoring & Protecting App Access (Defender for Cloud Apps):** Microsoft Defender for Cloud Apps (formerly Microsoft Cloud App Security, MCAS) is a Cloud Access Security Broker (CASB) solution integrated with Entra ID for deeper visibility and control over cloud app usage. It provides:

  * **Cloud Discovery:** Identify cloud apps and services being used (by ingesting firewall/proxy logs). This helps find shadow IT and assess risk of discovered apps via the **Cloud app catalog** which scores apps on security compliance.
  * **App Connectors:** Integrations (via APIs) with apps like Office 365, Salesforce, etc., to monitor activities and data in those services (e.g., scanning for sensitive information in files).
  * **Conditional Access App Control:** A real-time monitoring and control mechanism that works with Entra ID Conditional Access. When a CA policy routes a session through Defender for Cloud Apps, it can enforce **access policies** and **session policies**.

    * **Access policies** can *block or grant access* to an app based on conditions at session start (e.g., block download of Salesforce reports on unmanaged devices, or block access to an app from a risky IP).
    * **Session policies** enable in-session monitoring and control, like DLP and protection. For example, allow login to a web app but **monitor activities** and **prevent data exfiltration** – block file downloads, or apply protection (encrypt or label files) on download in real time. You can also block uploads of unlabeled files until the user classifies them, or prevent posting messages with sensitive info (e.g. in Slack or Teams). If users attempt to download malware or upload it, MCAS can scan and block those files immediately.
    * Users on **Edge** get an optimized experience (direct inspection), while other browsers are redirected through a proxy (\*.mcas.ms) for monitoring.
  * **Defender for Cloud Apps Policies:** In MCAS, you configure policies to detect risky behavior or enforce restrictions. Beyond CA-controlled sessions, MCAS can monitor OAuth apps. **OAuth app governance** helps you see third-party apps that users have consented to access your Office 365 data. You can **ban or approve OAuth apps** and get alerts if a malicious app is consented by many users.
  * **Alerts and Governance:** MCAS generates alerts for things like mass downloads, unusual admin activity, or impossible travel. It can automatically suspend users or require user **session re-authentication (Auth context)** if risky activity is detected (via integration with Conditional Access “Authentication context”).

  In summary, **Defender for Cloud Apps extends visibility and control**: it works across SaaS apps to apply your policies in real-time, beyond what Entra ID alone can do. For SC-300, focus on understanding that **Conditional Access** can trigger a session to be monitored by MCAS and that MCAS can enforce granular actions (block download, label file, etc.) to prevent data leaks.

* 🟡 **Hands-On Practice:** Try setting up a **Managed Identity** on an Azure VM or App Service and using it to access a storage account (e.g., assign a role to the identity and use Azure CLI/PowerShell with `az login --identity`). Practice an **App Registration**: create a test app in Entra ID, add a client secret, and grant it Graph API read access – then use Graph Explorer or Postman to authenticate with that client ID/secret. For **Conditional Access App Control**, review the MCAS portal (if available in your tenant) and understand the built-in policies. Microsoft Learn’s modules on **Implement and manage workload identities** and **Secure application access** are useful for step-by-step tutorials.

## Plan and Automate Identity Governance (20–25%)

* 🟢 **Identity Governance Overview:** Microsoft Entra ID Governance helps you ensure the **right people have the right access to the right resources** (and only for the right amount of time). It addresses questions like “Who should have access? Should they still have it? How do we review and certify access?”. Key features include **Entitlement Management, Access Reviews,** and **Privileged Identity Management**, plus tools to monitor identity risks and lifecycle.

* 🟢 **Entitlement Management (Access Packages):** Use this to govern the **identity lifecycle** of not just employees but also guests. An **Access Package** bundles resources (groups, Teams, SharePoint sites, apps, role assignments) that users can request access to as a single package. Access packages live in **catalogs**, which are logical containers often owned by a business unit or department. Delegated owners (like a department manager) can manage their catalog’s packages. When you set up an access package, you define:

  * **Who can request:** This can include internal users or external users from specific organizations (specified via **Connected Organizations**). For external partners, you can allow users from certain domains or tenants to request access.
  * **Approval workflow:** e.g., require the user’s manager or a package owner to approve the request (can have multiple stages of approval).
  * **Duration:** set **access expiration** (e.g., 90 days) after which access is removed unless re-requested or extended.
  * **Upon expiration:** auto-remove access by default. You can also force a new request if access is still needed.
  * **Additional options:** require **Terms of Use** acceptance (users must consent to a policy/terms document when requesting), or require justification.

  Once a request is **approved**, Entitlement Management automatically **assigns the user to all resources** in the package (adds to groups, assigns app roles, etc.) and even will add a B2B guest to your directory if they aren’t already there. When access expires or is revoked, it will **remove the user from those groups/apps and even remove the guest account from the directory** if they have no other assignments. This automation is powerful for managing contractors or guest access – no more lingering accounts after a project ends.

  *Example:* You create an “Project Atlas External Collaborator” access package containing a Team, a SharePoint site, and a SaaS app. You allow users from partner company Fabrikam to request it. A Fabrikam employee uses a redemption link to request access; their manager approves; they get added as a guest in your directory and immediately gain access to the Team, site, and app. In 60 days, an access review (or auto-expiry) removes them if they no longer need it.

* 🟢 **Access Reviews:** Regularly reviewing who has access helps ensure people’s access stays appropriate as roles change. **Access Reviews** in Entra ID allow you to schedule periodic reviews of group memberships, application access, or role assignments. Key points:

  * You can **plan reviews** for high-risk or sensitive resources – e.g., an access review for all guests in high-sensitive SharePoint sites, or for members of privileged roles.
  * When you **create an access review**, you define the scope (which group/app/role to review) and the reviewers. Reviewers can be the resource owners, the users’ managers, specific designated reviewers, or even allow **self-review** (users certify their own need for access). For guest user reviews, often a sponsor or internal owner is the reviewer.
  * Set the **frequency**: one-time or recurring (e.g., review this group quarterly). If recurring, reviews can auto-repeat and you can specify duration for each review period.
  * **Outcomes**: decide what happens when a reviewer **denies** continued access or if they **don’t respond**. For example, you might choose to **auto-remove access if not approved** by the reviewer by the deadline. Or require Azure AD to take no action but record the recommendations for manual processing.
  * During the review, reviewers see each user and can approve/deny continued access (and see insights like last login). Entra ID can provide **recommendations** (e.g., “deny – user hasn’t signed in in last 30 days”).
  * Once completed, the system will **remove users** who were denied or didn’t pass the review (if auto-removal is configured). For instance, a review of guest accounts can automatically clean up those that the reviewer marked as no longer needed.

  Use access reviews especially for **guest users** and **privileged roles** to maintain a clean, least-privileged environment. Microsoft even recommends an access review as a way to periodically **remove stale guest accounts** from your directory (govern the guest lifecycle).

* 🟢 **Privileged Identity Management (PIM):** This feature addresses the **privileged access lifecycle** – ensuring admin roles are tightly controlled. **PIM** allows you to make admin role assignments “eligible” instead of always active, so users activate roles only when needed (Just-In-Time access). Key PIM capabilities and terms:

  * **Eligible role assignment:** user has the potential to elevate to the role for a time, but is not always active.
  * **Activation:** the process of actually obtaining the role’s privileges – may require MFA, entering a business justification, and possibly approval by a designated approver.
  * **Time-bound access:** activations are temporary (e.g., 1 hour, 4 hours). PIM can also enforce *permanent* vs *time-bound* assignments and require renewals. You can assign roles as **permanent eligible**, **permanent active**, **time-bound eligible**, or **time-bound active** depending on scenario.
  * **Approvals:** PIM can be configured so that certain roles (or specific users activating) require approval each time. For example, a user can request the Exchange Admin role and a senior admin must approve via email/portal before the role is granted. PIM will handle sending the approval email and the workflow.
  * **MFA Enforcement:** You can require MFA on every activation (recommended) – even if the user is already logged in with MFA, PIM can demand a fresh MFA for that elevation.
  * **PIM for Azure AD roles vs Azure Resource roles:** PIM can manage **Entra ID roles** (directory roles like Global Admin, User Admin) *and* **Azure resource roles** (RBAC roles on Azure subscriptions/resource groups). It also can manage **Privileged Access Groups** (you can make membership of a group PIM-controlled – and that group could be tied to roles or resource access).
  * **Access Reviews for PIM:** PIM encourages reviewing role assignments regularly. You can even schedule access reviews for active or eligible role assignments via the Access Reviews feature.
  * **Audit and Alerts:** PIM provides an audit history of activations and changes. It can send alerts for suspicious or improper configurations (like too many permanent admins). All PIM activities (requests, approvals, activations) are logged for auditing.
  * **Break-glass accounts & PIM:** Microsoft recommends keeping a couple of emergency accounts outside PIM (as mentioned earlier) and then converting all other admins to eligible roles through PIM. PIM will also **prevent removal of the last active Global Admin** to avoid accidentally locking out all admins.

&#x20;*PIM Dashboard in Entra Admin Center, showing options to manage Azure AD roles, Azure resource roles, and privileged access groups. PIM enables just-in-time activation, approval workflows, and access reviews for admin roles.*

Overall, with PIM you **minimize standing admin access** – users elevate only when needed, with oversight. Know that only specific roles (Global Admin or Privileged Role Admin) can manage PIM settings. PIM settings can be fine-tuned per role (requiring approval, notifications on activation, etc.). Expect scenario questions on how to ensure an admin has to get approval or needs MFA to perform a task – PIM is usually the answer.

* 🟢 **Monitoring Identity and Access:** Strong governance includes monitoring logs and being able to answer “Who did what, when?” Entra ID provides:

  * **Audit Logs** – record of changes within Entra ID (e.g., user creation, group changes, application assignments). Useful for forensic questions like “Who added this user to admin role?”.
  * **Sign-in Logs** – record of authentication attempts by users and service principals, including success/failure and details on conditional access, device info, location, etc. Helps spot suspicious login patterns (impossible travel, unfamiliar locations).
  * **Provisioning Logs** – if you use Entra’s provisioning to sync users to SaaS apps (SCIM/B2B automation), these logs show status of user provisioning actions to apps.
  * **Workbooks & Insights** – Entra ID has built-in **workbooks** (interactive reports) for things like sign-in analysis, and **Identity Secure Score** which provides a score and recommendations to improve identity security. For example, enabling MFA for more users raises your score.
  * **Integration with Monitoring Tools:** You can configure **Diagnostic Settings** to send Entra logs to Azure Monitor Logs (Log Analytics workspace), Azure Storage, Event Hub or even a SIEM. This is crucial because the Entra portal only retains logs for 30 days by default (for P1/P2 tenants; 7 days for free tier). For longer retention and advanced analysis, send logs to a Log Analytics workspace and use **Kusto Query Language (KQL)** queries to slice and dice data. For example, query sign-in logs to find all logins from a specific country or all failed logins for a particular app. You can also stream logs to **Microsoft Sentinel** (Azure’s SIEM) or third-party SIEM via Event Hub.
  * **Identity Protection reports** – if using P2, monitor the Risky Users, Risky Sign-ins, and risk detections reports to catch accounts under attack. Set up alerts for these.
  * **Entra Health** – there’s also a “Microsoft Entra Health” section that shows the health of the Entra services and any tenant-specific issues (like sync errors, etc.).

  Be prepared to recommend solutions for monitoring: e.g., **“How to retain sign-in data for more than 30 days?”** – send to Log Analytics; **“How to detect when an admin role is assigned outside of PIM?”** – use Azure AD audit logs (possibly set an alert or use Sentinel analytics). Also, know that **Identity Secure Score** and **Entra Recommendations** in the portal will highlight gaps (like not all users registered for MFA) – a good governance practice is to follow those recommendations to improve your score.

* 🟡 **Exam Tips:** Expect scenario questions tying these topics together. For example, a scenario of a new contractor onboarding process might involve **Entitlement Management** (access package for contractors), **Access Reviews** (to periodically check their access), and **PIM** (if they need privileged roles). When you see **keywords** like “temporary admin access” or “just-in-time,” think PIM; for “regularly ensure guests still need access,” think Access Reviews; for “automate user account provisioning and deprovisioning from HR,” know that Entra ID can integrate with HR systems (Workday/SuccessFactors inbound provisioning) and Lifecycle Workflows (for automation on user joiner/leaver events). The exam is open-book but limited to MS Learn – use the documentation (like the links provided in these notes) to lookup specifics quickly (e.g., what settings are in an access package policy, or how to configure a certain Conditional Access rule). These notes summarize key points, but the documentation can provide the exact steps or options if you need to double-check during the exam.
